# ADR-005: S3 for Raw Document Storage

## Context
The Knowledge Acquisition Platform ingests unstructured content from the web. The raw HTML/Markdown files, crawl runs, and large document artifacts need to be stored reliably, cheaply, and with versioning to preserve provenance and support re-processing without re-crawling.

## Decision
We will use an S3-compatible object storage system (AWS S3 in production, MinIO locally) for storing raw ingestion artifacts, documents, and processed files.

## Alternatives
- Storing raw HTML in PostgreSQL or MongoDB: This would bloat the databases, degrade performance, and significantly increase storage costs.
- Local File System: Does not scale horizontally, lacks built-in redundancy, and complicates containerized deployments.

## Advantages
- Infinite scalability and cost-effective storage for large binary/text objects.
- Built-in versioning and lifecycle management.
- Easy to serve static assets via CDN (CloudFront) if needed.
- Standardized API (S3 API) supported by MinIO for local development.

## Disadvantages
- Eventual consistency (historically, though S3 now offers strong read-after-write consistency).
- Requires managing object keys/paths securely and tracking them in the primary database (PostgreSQL/MongoDB).

## Consequences
- A strict object key naming convention (e.g., `raw/{document_id}/v{version}/page.html`) will be enforced.
- The databases will only store the S3 URIs (pointers), not the raw content.

## Status
Accepted
