# ADR-004: Redis/BullMQ for Asynchronous Jobs

## Context
The system performs numerous asynchronous, long-running, or resource-intensive tasks such as web crawling, document chunking/embedding, code execution processing, and generating learning roadmaps. These require reliable queuing, retries, concurrency control, and scheduling.

## Decision
We will use Redis combined with BullMQ to manage asynchronous job queues.

## Alternatives
- RabbitMQ / ActiveMQ: Robust message brokers, but heavier and more complex to configure for simple job queues compared to Redis.
- AWS SQS: Fully managed, but lacks built-in advanced job state management (like delayed jobs, rate-limiting, parent-child jobs) out of the box without additional orchestration, which BullMQ provides natively.

## Advantages
- High performance, low latency in-memory data store.
- BullMQ provides rich job management features: retries, delays, rate-limiting, and UI dashboards.
- Redis can also serve double duty for short-lived caching and rate limiting.

## Disadvantages
- Data in Redis queues is lost if the Redis instance crashes without proper persistence (AOF/RDB) configured.
- Memory-bound; large payloads must be stored externally (e.g., S3) and referenced by ID in the job payload.

## Consequences
- Redis will not be used as a system of record.
- Large job payloads (like raw HTML) will be stored in S3, with object URIs passed in Redis messages.
- Specific queues will be defined for discovery, fetch, process, classify, chunk, embed, and evaluation.

## Status
Accepted
