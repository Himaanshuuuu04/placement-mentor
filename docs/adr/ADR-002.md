# ADR-002: PostgreSQL as Transactional Source of Truth

## Context
The system must maintain complex relational data regarding users, profiles, companies, questions, assessments, submissions, and mastery states. This data requires ACID compliance, relational integrity (foreign keys), and structured querying capabilities.

## Decision
We will use PostgreSQL as the primary system of record for transactional and application state.

## Alternatives
- MongoDB for all data: Flexible schema but lacks robust multi-document ACID transactions and enforces relational joins at the application layer, which is suboptimal for highly structured entity relationships like RBAC or mastery tracking.
- MySQL: Viable, but PostgreSQL offers superior JSONB support, advanced indexing, and better extensibility (e.g., pgvector if needed, although MongoDB is chosen for vector search here).

## Advantages
- Strong ACID compliance ensures data consistency for critical domains (evaluations, mastery).
- Powerful relational features (constraints, foreign keys) enforce data integrity.
- Excellent JSONB support allows storing flexible metadata alongside relational data.

## Disadvantages
- Schema migrations require careful management.
- Vertical scaling limits, though adequate for the expected load of a college project before complex sharding is needed.

## Consequences
- Strict normalized schemas will be designed for transactional domains.
- ORM/Query builders will be used with strict migration management.
- AI agents will not directly modify PostgreSQL; they will use service APIs.

## Status
Accepted
