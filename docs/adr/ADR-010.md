# ADR-010: Event-Driven Architecture for Asynchronous Workloads

## Context
The platform consists of multiple microservices that need to react to changes in state without tight coupling. For example, when a code submission is evaluated, the Knowledge Tracing service needs to update the student's mastery model, and the Roadmap service may need to generate a new learning path.

## Decision
We will implement an event-driven architecture (EDA) for cross-service asynchronous communication using a message broker (e.g., Redis Pub/Sub or AWS EventBridge/Kafka).

## Alternatives
- Synchronous REST/gRPC calls: Tight coupling. If the Mastery Service is down, the Evaluation Service would block or fail, cascading failures.
- Database triggers/polling: Poor scalability, high latency, and couples services to a shared database schema.

## Advantages
- Loose coupling: Producers do not need to know about consumers.
- Improved resilience: Services can fail or restart without dropping events (if durable queues/logs are used).
- Enables complex downstream workflows (like updating mastery, generating roadmaps, sending notifications) triggered by a single action.

## Disadvantages
- Eventual consistency: Read models may lag slightly behind write models.
- Difficult to debug and trace flows without robust correlation IDs and distributed tracing.

## Consequences
- Standardized event schemas (e.g., `EventID`, `EventType`, `CorrelationID`, `Payload`) will be enforced.
- Services must be designed for idempotency to handle potential duplicate event deliveries.
- Synchronous API calls will still be used for immediate user-facing reads and explicit commands.

## Status
Accepted
