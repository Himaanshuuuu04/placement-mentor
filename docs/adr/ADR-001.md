# ADR-001: Microservices Architecture

## Context
The "AI-Powered Agentic Placement Mentor" requires supporting varied workloads including student interactions, long-running background tasks (web ingestion, code execution), and AI agent orchestration. A monolithic architecture would couple these distinct scalability and reliability requirements, potentially leading to bottlenecks. The system must support independent scalability of high-load components and clear service ownership.

## Decision
We will use a modular microservices architecture with clear bounded contexts (e.g., API Gateway, Identity, Assessment, Knowledge Tracing, Agent Orchestrator, Code Execution).

## Alternatives
- Monolithic Architecture: Simpler to deploy initially, but hard to scale specific workloads like code execution or web crawling independently.
- Serverless-only (Functions): Highly scalable but complex state management and potentially high latency for real-time interview scenarios (cold starts).

## Advantages
- Independent scalability of resource-intensive components (e.g., Crawlers, Code Execution, AI Agents).
- Clear boundaries and data ownership.
- Fault isolation; a failure in the Crawler Service doesn't take down the Student Learning Platform.

## Disadvantages
- Increased operational complexity (deployment, networking, observability).
- Requires careful design of asynchronous communication and event-driven data consistency.

## Consequences
- Requires a robust API Gateway and event bus for inter-service communication.
- No direct database access between services; data must be accessed via APIs or events.
- Distributed tracing and centralized logging become mandatory.

## Status
Accepted
