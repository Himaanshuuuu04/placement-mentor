# ADR-009: WebSocket and WebRTC Split for Real-time Interactions

## Context
The system supports two distinct real-time workflows: text-based interactions (real-time chat, code syncing, typing presence) and audio-based interactions (mock technical interviews).

## Decision
We will use WebSockets for real-time text, events, and session presence, and WebRTC specifically for real-time audio and media streaming.

## Alternatives
- WebSockets for everything (including audio): Sending raw audio chunks over WebSockets via TCP suffers from head-of-line blocking, causing lag and jitter which degrades interview quality.
- WebRTC for everything: Using WebRTC data channels for text is possible but overcomplicates simple event broadcasting and requires complex NAT traversal/STUN/TURN for data that a simple WebSocket proxy could handle.

## Advantages
- WebSockets provide reliable, ordered delivery over TCP, ideal for text, JSON events, and code editor synchronization.
- WebRTC uses UDP (primarily), minimizing latency for audio streams, handling packet loss gracefully, and providing built-in echo cancellation and noise suppression.

## Disadvantages
- Requires managing two different real-time protocols and infrastructure (WebSocket Gateway + WebRTC Signaling/Media Server).

## Consequences
- A Realtime Gateway service will be responsible for WebSocket connections.
- WebRTC will be used strictly when an audio interview session is initiated, using WebSockets for the initial signaling.

## Status
Accepted
